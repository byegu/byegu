## 1. 접수와 완료를 구분하는 화면

결제 요청은 API 접수 뒤 지갑 서명, 체인 작업, 주문·결제 상태 반영을 거칩니다. 요청을 보냈다는 사실만으로 결제 성공을 판단하면 처리 중인 요청을 완료로 안내할 수 있습니다.

`PaymentPage.tsx`에서 서명 대기·처리 중·성공·실패 상태를 구분했습니다. 최신 주문·결제 조회 또는 체인 작업으로 성공이 확인된 경우에만 완료 화면으로 이동하도록 했습니다.

## 2. 실패한 작업과 재시도를 분리

재시도 전에는 주문과 결제의 최신 상태를 다시 조회했습니다. 아직 처리 중이면 중복 실행을 막고, 실패한 체인 작업은 복원하지 않도록 했습니다. 다시 시작할 때는 새 멱등키로 서명 절차를 재개했습니다.

서버 반영 지연과 오래된 화면 상태를 구분하고, 사용자의 재시도 입력이 겹치는 경우도 확인했습니다. 이는 프론트엔드 복구 경계이며, 전체 결제 시스템의 중복 방지나 실제 운영 안정성을 보장한다는 뜻은 아닙니다.

## 3. 확인한 범위

`PaymentPage.live.test.tsx`로 다음 상황을 확인했습니다.

- 결제 정보 생성 전 404 응답
- 409 상태 충돌과 주문·결제 반영 지연
- 실패 뒤 새 서명으로 재개
- 처리 중 또는 연속 입력에 의한 중복 재시도

2026.09.29 해당 파일의 표적 실행에서 **31개 테스트가 통과**했습니다. 이 수치는 그 파일의 단일 실행 결과이며, 프로젝트 전체 테스트 수나 운영 성과가 아닙니다.

## 사용 기술

React · TypeScript · Web3Auth · Kaia

## 결과와 회고

최종 발표까지 맡은 화면 흐름을 구현했습니다. 이 과정에서 비동기 요청의 성공 응답과 업무 완료를 같은 것으로 처리하지 않고, 최신 상태를 근거로 화면을 전환하는 기준을 세웠습니다. 결제 성공률·정산 정확도·운영 장애 감소율은 확인된 수치가 없어 제시하지 않습니다.
